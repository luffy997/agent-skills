# Sensitive Info Guard

## 目标与边界

作为 **Git 提交前最后一道隐私与凭据检查**。用户要求提交代码时，应先审查本次即将进入提交的内容，不得直接 `git commit`。

- 仅扫描本地文件与 Git 暂存区；默认不把待提交代码、词库或匹配值发送到外部服务。
- 不依赖特定的公司、人名或客户知识；用户提供的私有名单只作为本地匹配依据，不得写进公开仓库、提交信息或外部提示词。
- 这是 Agent Skill，不是操作系统级 `pre-commit` 钩子：只有在支持并加载此技能的代理处理提交请求时生效，不能拦截用户绕开代理直接执行的 `git commit`。
- 除非用户明确要求，**只提交，不推送**。不得通过 `--no-verify` 绕过已有钩子。

## 工作流

### 1. 确认仓库和提交范围

在目标仓库执行：

```bash
git rev-parse --show-toplevel
git status --short
git diff --cached --name-status
git diff --name-status
```

优先使用用户明确指定的文件。若已暂存，默认以暂存区为本次提交的权威范围；若未暂存，仅选择与当前任务有关的文件加入暂存，**不要盲目 `git add .`**。不确定文件归属或涉及其他人改动时，询问用户而非擅自提交。未跟踪文件尤其需审查后再添加。

记录 `git diff --cached --name-only -z`，支持空格等特殊文件名。重命名、删除和二进制文件也要纳入风险判断。检查是否有子模块或符号链接异常。

### 2. 审查实际提交快照

首选以下命令读取暂存区内容，避免用工作区版本代替将提交的版本：

```bash
git diff --cached --check
git diff --cached --binary --no-ext-diff
```

对于新增或改动的文本文件，通过 `git show :path/to/file` 读取 **暂存区完整版本**（必须正确处理特殊路径）；同时关注新增的行和上下文，避免只看新增行却漏掉已存在敏感配置。不得把 `git diff` 输出直接复制到远端服务。

对新增的二进制、压缩包、数据库、证书等无法充分查看的文件进行风险提示；如含未知内容且无法确认安全，应中止提交。大型文件可优先检查文件名、类型和抽样，但无法检查完整内容时应明确告知覆盖缺口，不能宣称安全。

### 3. 两层扫描

**确定性规则（必须执行）**：

- 凭据：明文密码、认证令牌、私钥及其头部、云服务密钥、数据库连接串、含用户名密码的 URL、`.env` / `id_rsa` / `*.pem` 等敏感文件。
- 网络与基础设施：内网 IPv4/IPv6、真实公网服务器地址、内部域名、机器名、数据库地址与端口、内网接口、绝对路径中包含的用户身份。
- 身份与组织：企业邮箱、手机号、个人邮箱、公司全称/简称、客户名称、部门、项目代号、合同/工单编号、人名、客户现场位置。
- 文档：README、SKILL.md、参考资料、示例命令、终端日志、截图、注释、测试数据；这些内容与代码一样检查。

检查上下文，区分真实值与占位符（如 `example.com`、`127.0.0.1`、`YOUR_API_KEY`、RFC 5737 文档示例地址）。**不要因为单独出现 `password` 等变量名就认定泄漏**；不能仅靠正则猜测所有人名或公司名称，对语义隐患做保守的人工审阅并标记不确定性。

若本机已有 `gitleaks`，可额外对待提交内容执行离线扫描。不要为安装工具自动上传代码或执行不可信安装命令。没有工具时完成内置规则与语义审查，不应跳过审查。

**语义审查（必须执行）**：阅读本次提交中面向公开仓库的自然语言文本、注释、脚本样例与路径，识别隐含披露：客户现场经历、企业内部研发细节、实际部署拓扑、真实人员关联、私有服务名称等。按 `references/checklist.md` 判断风险等级。

### 4. 作出提交决策

- **阻断**：真实凭据、私钥、明确可识别的私有组织/客户信息、应保密的人名或个人信息、明显真实的内部配置、无法检查的高风险内容。**不得自动提交**；优先建议改为占位符、环境变量、匿名名称或脱敏示例。
- **需确认**：疑似真实的公网 IP、组织或人名、可能属于公开信息的内部术语、无法确定性质的内容。先展示脱敏后的证据和风险原因，获得明确确认或修订后再提交。
- **可通过**：测试用保留地址、明确的虚构样例、常见变量名及已验证无敏感值的内容。

报告包含 `文件:行号`、类别、等级、原因与安全替换建议。**默认对匹配值遮掩**，例如 `10.*.*.12`、`a***@example.com`、`sk-***`；不要在报告或提交消息中重复完整敏感值。

### 5. 提交与复核

如果没有阻断项或未决风险：

1. 再次执行 `git status --short` 与 `git diff --cached --check`。
2. 核对待提交文件列表，防止审查之后暂存区发生变化；发生变化必须重新扫描。
3. 生成简明准确的提交信息，不包含客户、人员或内部项目标识。
4. 执行 `git commit -m "..."`，保留并尊重现有钩子。
5. 返回提交哈希、文件数、检查结论及仍存在的非阻断提醒。

若用户仅要求“检查能不能提交”，**只审查，不提交**。若存在阻断或待确认项，先停止操作，报告后等待用户处理；不得擅自删除或修改文件以强行通过。

## 输出格式

```text
提交前敏感信息检查：通过 / 阻断 / 需确认
范围：N 个暂存文件（或拟提交文件）
检查：凭据 / 地址 / 个人与企业信息 / 文档与语义
发现：高风险 N、待确认 N、提示 N
问题：路径:行号 — 类型 — 脱敏证据 — 建议
结果：已提交 <短哈希> / 未提交（原因）
```

详细判定与误报处理见 [检查清单](references/checklist.md)。
